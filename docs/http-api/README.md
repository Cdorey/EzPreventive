面向前端与后端开发者，以网络可观察行为为边界；使用接口不需要理解对方的类、数据库或页面实现。本文档对应当前 2.2 源码，包含维护清理功能；部署方应确认实际运行版本及已发布功能。

## 通用约定

- 文中的 `/Auth/...` 等路径相对于应用部署基路径，不包含 API 版本前缀。例如部署在 `/nutrition` 下时使用 `/nutrition/Auth/Login`。
- 普通请求与响应使用 UTF-8 JSON、camelCase 字段；单独注明的表单、文件、重定向、空响应和 SSE 除外。JSON 请求发送 `Content-Type: application/json`。
- GUID 是字符串；日期时间使用 ISO 8601 UTC，接收端应支持 `Z` 和 `+00:00`。`startTime` 是服务器本地每日时间，不是 UTC 时间戳。
- 普通枚举使用 JSON 整数；AI 膳食枚举使用字符串，见对应文档。不要把显示名称当作传输值。
- “已登录”表示 `Authorization: Bearer <accessToken>`；“管理员”要求角色 `Admin`；“AI 权限”要求 `Permission=Prescription` 声明，单有管理员角色不等于拥有该权限。
- 列表接口未提供分页、排序参数或总数信封，除明确说明外不要依赖结果顺序。忽略不认识的新增响应字段，保留版本等不透明标识的原值。
- 204 与空正文 200 不应交给 JSON 反序列化。文件响应按二进制读取，SSE 按流读取。

## 错误与重试

当前 API 没有统一错误信封。调用方先检查状态码和 Content-Type，再按接口解释正文：

| 场景 | 状态与正文 |
| --- | --- |
| 认证失败 | 通常 401，`{code,message}`，详见认证文档；少数动作也会返回空 401 |
| 已认证但权限不足 | 403，不保证 JSON 正文 |
| JSON、类型或字段验证失败 | 通常 400 ValidationProblemDetails，含 `status`、`title`、`errors`；框架还可能返回 415 或请求过大时的 413 |
| 业务校验失败 | 400；按端点可能是文本、`{success,message}` 或错误数组 |
| 不存在 | 404；正文可能为框架 ProblemDetails、文本或空，不统一转换成空列表 |
| 并发冲突 | 409；认证/审批为 `{code,message}`，维护配置为 `{key,message}`，角色重名为文本 |
| 限流 | 429，不保证业务错误正文 |
| 服务异常 | 5xx，正文不属于稳定业务契约 |

错误文案只用于展示，程序分支依赖状态码及文档列出的稳定错误码。网络失败不证明操作未执行。删除、审核、发信和 AI 生成不可因超时直接无条件重发；先重新读取状态。刷新凭据一次性使用，响应丢失后同样不能盲目重发旧凭据。

当前限流：登录每 IP 每分钟 10 次；刷新和退出共享每 IP 每分钟 120 次；注册、邮箱确认和恢复类接口共享每 IP 每分钟 5 次；修改密码、申请换邮箱和修改手机号共享每用户/IP 每 5 分钟 5 次。多个动作会消耗同一策略配额。

## 从 2.1 升级

以 `v2.1.0.0` 为基线：

1. `/Auth/Login` 从表单改为 JSON，从 JWT 字符串改为令牌对象；新增刷新、退出和浏览器认证端点。
2. 旧 JWT 缺少会话标识，不能直接用于 2.2，用户需要重新登录；受保护接口采用新的认证错误码。
3. 两个认证申请列表新增 `version`；`/Admin/UpdateRequest` 必须携带非空版本，成功返回新版本，并增加并发与状态限制。
4. 新增维护配置与账号清理端点。营养数据和 AI SSE 在本次代际升级中未改变契约。

客户端内存管理和自动重试实现见[认证会话实现](../authentication-sessions.md)；发布版本规则见[版本管理](../versioning.md)。
