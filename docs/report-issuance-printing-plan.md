# 报告签发与打印工作方案

状态：按讨论方案实施中。更新日期：2026-09-09。

工作分支：`codex/report-issuance-printing`，基于 `codex/2.2.0-integration` 的 `6ed3788`。

## 1. 已确定的设计边界

- 新增签发报告和打印报告两个独立 Permission；签发权限首版仅授予经核验的医师。
- 首版先以几种现有营养量表报告试行；咨询总报告及其他模块报告放到后续扩展。建议试行名单为 NRS 2002、MNA-SF、MUST，具体模板仍需确认。
- 前端沿用现有 JWT Claims、认证状态和 `AuthorizeView` 的授权规则。操作入口复用同一 policy，避免只隐藏按钮却遗漏正常调用路径；不增加独立的离线授权凭据或客户端验签体系。
- 报告制作、签发确认、成品保存和打印在本机完成。这些功能不新增患者资料、报告内容、PDF 或报告指纹的上传。
- 报告内容与流程由 Blazor 侧及其共享 Application 代码处理，浏览器/WPF 宿主承担本机文件与打印适配；不按网络通断另建报告工作模式，也不把离线登录恢复列为本轮工作。
- 账号登录、现有参考数据查询和用户主动发起的 AI 功能有各自的网络边界；报告操作不能暗中触发 AI 生成或远程重算。
- 未签发内容输出带水印的评估稿；已签发正式报告输出保存的无水印原件。水印取决于报告的状态和用途，不取决于打印者是否拥有签发权限。
- 已签发报告同时产生档案契约中的 `NutritionReport` 记录和可供重印的成品。
- 多个业务模块可以分别放置签发、打印按钮，共用报告流程；每份报告分别记录签发范围及状态。
- 签发表示软件内的人员确认与版本冻结。这一方案不提供独立的身份真实性证明、不可篡改电子签章或自动免责承诺。
- 用户明确要求优先复用现成字段和处理机制：先使用现有版本、生命周期、引用及校验能力；不为同一语义叠加 `nextReport`、`IsVoided` 或另一套报告状态。只有现有能力确实无法表达需求时，再讨论最小扩展。

## 2. 当前实现与必须处理的差异

| 当前实现 | 对本功能的影响 |
| --- | --- |
| `PolicyList` 已统一注册基于 Claims 的 Permission | 可扩展现有策略，不需要另建权限系统 |
| 原 `Printer.razor` 自动打印占位页面已移除，且没有调用方 | 报告入口统一使用实际 PDF 与宿主打印能力 |
| `NutritionReportResource` 已表达用途、确切输入版本、模板、参与人员及成品指纹 | 优先复用；PDF 字节和宿主路径不进入该资源 |
| XML codec 已认识 `NutritionReport` | 主要缺口在运行态组装、签发用例、成品存储及报告调阅 |
| `ArchiveWorkflow.SaveCurrentAsync` 按咨询逻辑 ID 覆盖草稿文档 | 正式报告不能复用这一覆盖入口 |
| 运行态资源的草稿版本 ID 被重复使用 | 签发快照必须获得不会被后续草稿修改的确切版本 |
| `ConsultationDocument` 要求一个 Patient、一个 Consultation，且全部临床资源反向引用该 Consultation 的确切版本 | 多次签发的不同咨询快照不能直接堆入同一咨询文档 |
| 档案列表和复诊历史按咨询处理 | 新增报告存储后，不能把每份报告快照误算成一次复诊，也不能让局部报告替换整次咨询的历史事实 |
| 登录与权限已有统一的前端会话语义 | 本轮复用，不扩展离线登录或另建网络状态分支 |

## 3. 权限及界面行为

暂定字段名 `IssueReport` / `PrintReport`，策略名 `IssueReportPermission` / `PrintReportPermission`。按现有反射注册方式，实际 Claims 分别为 `Permission=IssueReport` 和 `Permission=PrintReport`。

| 权限组合 | 签发 | 当前未签发内容 | 已签发正式报告 |
| --- | --- | --- | --- |
| 两者都没有 | 不允许 | 不提供应用内打印 | 调阅遵循现有档案访问规则，不提供应用内打印 |
| 只有 PrintReport | 不允许 | 可以打印带水印评估稿 | 可以重印原件 |
| 只有 IssueReport | 可以 | 不提供应用内打印 | 可以签发归档，不提供应用内打印 |
| 两者都有 | 可以 | 可以打印带水印评估稿 | 可以重印原件 |

授权授予沿用现有账号、角色及 Claims 管理入口。新增权限不会因为用户已有 `Prescription` 权限而自动获得，也不把所有医师角色无条件升级为签发者。打印权限的实际角色分配在发布说明中明确，由管理员配置。

模块按钮使用共享的可用状态及拒绝原因：无权限、报告资料不齐、正在处理、当前宿主不可用等。展示判断与执行判断使用相同的权限来源。签发时再次读取当前账号，不能沿用打开预览时已经退出或切换的账号。

建议的按钮行为：

- “签发报告”：进入当前模块报告的审核预览；已签发后有修改时，明确当前内容尚未签发。
- “打印”：未签发时进入带水印预览；有历史正式报告且当前内容已修改时，明确区分“当前评估稿”和“已签发报告”。
- 档案库的“再次打印”：选定确切报告，读取原件，不读取当前工作区数据。
- 如果提供 PDF 下载，与应用内打印采用同一个 PrintReport 权限，避免形成另一套输出规则。

PrintReport 管理应用自身提供的输出入口，无法控制操作系统截图、浏览器自身打印和已经导出文件的外部使用。

建议水印文案：`仅供教学或功能评估使用 · 未经医师审核签发`。水印和固定页脚均进入评估稿成品，每页可见，不依赖打印背景色选项。最终文案随模板确认。

## 4. 数据、成品与签发流程

### 4.1 数据与成品的职责

- 现有咨询草稿：继续用于当前业务数据保存。
- 签发快照：保存报告所属患者、咨询及所需资源的引用闭包，内容不可原地覆盖。
- NutritionReport：记录报告用途、标题、确切输入版本、模板版本、作者及签发人事实、签发时间和成品指纹。
- PDF 成品：保存实际交付的分页、文字、图表、字体和签发信息。原件的字体、图片等资源自包含。
- 报告索引：按患者、咨询、报告类型和报告标识关联快照与成品，支持一个咨询下多份报告。

建议给报告快照和成品建立独立的本机存储入口，按报告标识/版本定位，不与当前咨询草稿共用覆盖键。保留逻辑资源身份，为冻结的资源分配适当的独立版本并统一映射内部引用；不得让相同版本 ID 在草稿和正式快照中表示不同内容。

优先保持现有 Contracts 与 XML 的职责。报告类别由共享的报告定义提供稳定标识、内容范围和模板信息；若需要契约扩展，先明确现有字段无法表达的语义，不用标题充当稳定类别标识。

### 4.2 签发步骤

1. 按现有 policy 检查签发权限，核对当前签发人资料和所选报告范围。
2. 校验该报告的必要数据及完成状态。签发条件属于业务层，不把所有草稿保存要求提升为正式报告要求。
3. 捕获不可变的待签发快照，准备成品预览。预览绑定具体数据和模板；后续工作区编辑不能悄悄进入待签发内容。
4. 医师确认预览内容。提交前复核账号、权限及快照是否仍为用户确认的版本；发生变化则重新确认。
5. 固定签发信息，生成最终 PDF，计算确切字节的指纹，完成 NutritionReport 映射和契约校验。确认过程必须覆盖最终成品，不能在确认后再改变临床内容或版式。
6. 持久化快照、报告记录、成品及可见索引。全部可用后才显示“签发完成”。
7. 有打印权限时，可继续打印已经保存的原件。

签发信息中的姓名、机构及时间一经保存，不随账号资料或设备时区变化而重写。输入完整性校验不等于软件保证临床结论正确。

### 4.3 失败、重试与后续修改

- 重复点击和同一请求重试复用操作标识；普通重印不产生新报告。
- 渲染、校验或保存失败，不产生可见的“已签发但没有成品”的记录；允许重试并处理未完成写入。
- 签发成功后取消打印或打印失败，不撤回签发，也不重新生成报告。
- 已签发原件缺失或指纹不符时，停止重印并明确提示；不能使用最新模板重新生成后冒充原件。
- 修改当前咨询不会改变历史报告；修改后的内容必须重新确认，才可产生新的正式输出。
- 对同一报告的更正采用版本链方向，建议复用新版本的 `Supersedes` 指向被替代的确切旧版本，界面需要的 `nextReport` 由此推导。具体规则见 D2。
- 只有新版完成签发并提交成功，替代关系才生效；新建草稿、打开预览、签发失败都不能让旧报告失效。

### 4.4 保存和交换

浏览器以 IndexedDB 保存报告索引、快照和 PDF；桌面使用受管理的文件及索引。共享层规定“提交成功后所有组成部分可用”，各宿主负责事务或暂存、提交和恢复策略，不假设多个文件写入天然具备事务性。

建议增加包含清单、XML 快照和 PDF 的报告交换包，与现有纯 XML 导出并存。只携带 XML 的旧文档仍可以调阅，但缺少 PDF 时不能承诺原样重印。导入包核对引用、媒体类型和指纹；不把这些完整性检查宣称为医师身份的独立认证。

档案删除、清空、备份和导入需要覆盖相应成品及索引。删除有报告的咨询时应展示影响范围；删除本机文件与业务上的“作废报告”是不同操作。具体是否允许单独删除正式报告，在 D2 中一起确定。

## 5. 项目职责建议

接口名称为规划占位，不要求按名称机械建立新项目或并行机制。先盘点并复用现有档案工作流、codec、宿主文件交互与存储实现；新端口只用于现有接口确实缺失的成品渲染、不可覆盖提交和打印能力。契约字段已经存在，不代表相应运行态用例已经实现。

| 位置 | 工作内容 |
| --- | --- |
| Shared / Policies | 两个 Permission 和既有授权配置的接入 |
| Domain / Assessments.Common | 量表公共模型、具体定义与计分规则；不增加 PDF 排版字段 |
| Application / Reports | 报告内容范围、快照、签发条件、用例编排、成品一致性，以及必要的渲染/存储/打印端口 |
| Archives.Contracts | 复用 NutritionReport 与元数据；只在明确存在语义缺口时扩展 |
| Archives.Xml | 必要的兼容和 round-trip 验证，不承担 PDF 字节存储 |
| UI | 共享报告操作组件、状态、预览反馈及档案报告清单 |
| Presentation | 认证状态/policy 适配、页面与用例连接、共享报告模板及 pdfmake 适配和本地静态资源 |
| Client / WPF | PDF 存储、文件交换、各自的预览与实际打印；不复制共享模板 |
| Server | 复用现有账号权限管理；本轮报告用例不新增接收患者数据的接口 |

报告布局及内容投影尽量跨宿主共享。两个宿主只分担平台差异，不各自实现一套临床内容、水印规则或签发逻辑。

## 6. 分阶段实施与验收

### 阶段 0：确定量表模板和版本链的业务口径

- 确定 D1 的试行名单与模板、D2 的单独作废及历史打印规则；D3 已明确为复用现有登录与权限机制。
- 列出首份报告的字段、签发必填项、页眉页脚、署名方式和水印文案。
- 使用合成数据制作可审阅样张，覆盖长姓名、长结论和多页情况。

交付：报告规格及样张；不以实际患者数据作为开发样本。

### 阶段 1：验证本机 PDF 与两个宿主的打印路线

- 比较可用于当前 .NET/WASM/WPF 组合的本机渲染方案，核对依赖及中文字体的分发许可。
- 验证分页、中文字体、图表、长表格、页码、每页水印和本机打印交互。
- PDF 所需资源随程序或成品提供，避免报告渲染依赖远程字体、图片和服务。
- 用同一份 PDF 验证浏览器与 WPF 的重印路线。

交付：可运行的技术验证和选型结论。若发现只能通过上传报告渲染、需要新的商业授权，或无法支持其中一个宿主，先讨论取舍再选定实现。

### 阶段 2：建立共享权限和报告用例

- 接入两个 policy、操作状态和共用按钮组件。
- 建立报告定义、数据快照、签发条件和操作结果模型。
- 明确预览、确认、保存成功与打印各自的状态；完善取消和重复操作处理。
- 对旧账号说明新增权限的配置方式，避免自动扩大授权。

交付：同一权限矩阵在展示及执行入口中一致生效，四种权限组合均可验证。

### 阶段 3：签发记录、不可变快照和成品存储

- 实现快照版本与内部引用映射、NutritionReport 组装及正式校验。
- 在两种宿主中保存报告及成品，完成提交、失败恢复和读取校验。
- 根据 D2 落实再次签发、修订/作废及旧版保留语义。
- 验证旧草稿保存、档案调阅、复诊历史和旧 XML 兼容。

交付：一份报告可以签发、重启后读取并重印；修改草稿不影响原件。

### 阶段 4：档案库与首批模块接入

- 档案库按患者、咨询展示报告列表、用途、签发人、时间及版本/状态。
- 提供原件查看、再次打印、成品不可用提示和必要的版本选择。
- 按 D1 顺序接入试行量表；每种模板分别确认内容范围和签发条件。咨询总报告及其他模块后续扩展。
- 接入报告包导入导出以及关联附件的备份、删除和清理。
- 独立量表速查和 DRIs 速查建议先提供评估稿打印；正式报告需关联明确的患者和咨询。

交付：工作区签发到档案库重印形成完整流程。

### 阶段 5：集中验收与发布准备

- 验证报告操作不新增患者数据网络请求，也不隐式重跑参考查询或 AI。
- 验证权限组合、账号切换、无权限操作和现有会话失效时的行为。
- 验证重复签发、存储中断、打印取消、成品损坏和多窗口竞争。
- 验证应用/模板/账号资料/显示时区变化后，历史 PDF 字节保持一致。
- 用合成样本完成中文、多页、长表格、图表和水印的视觉验收。
- 运行受影响项目测试、架构检查及 Release 构建；两个宿主分别进行实际预览与打印验收。
- 更新功能说明、权限配置、存储备份和版本兼容文档。

“一致”验收针对报告内容、版式和保存的 PDF 原件；打印机色差、纸张设置和用户手动缩放需在打印说明中明确。

## 7. 讨论结果与剩余决策点

### D1：首版量表报告试行（范围已收敛，模板待定）

用户已明确先以几种量表报告试行。建议选择仓库已有实现的 NRS 2002、MNA-SF、MUST，共用报告框架和签发流程，再分别验证各自的题目、评分和结果展示。

建议首版模板包含患者与咨询基本信息、量表名称及版本、实施时间与实施者、适用题目及实际回答、已有评分贡献/总分/分级、必要的解释以及签发人和时间。报告读取已有评估快照，不重新解释量表规则；跳过、不适用和缺失回答按原始事实表达。

建议首版保留逐题回答与结果，使用共用版式，随实际样张确认分页和详略。咨询总报告、SOAP 与 AI 正文暂不进入试行报告范围。

### D2：用版本链表达替代，单独作废及旧版输出仍需确定

用户提出以类似链表的 `nextReport` 表达旧报告失效。该思路适合新版替代旧版，建议按以下方式实现：

- 使用现有 `ResourceMetadata.Supersedes`，由新版本指向它替代的旧版本；同一报告保留逻辑 ID，不同修订有独立版本 ID。界面的 `nextReport` 是反向查找结果，不另维护第二套权威指针。
- 有已提交的正式后继版本，表示旧版“已被替代”。“没有后继”只表示链末端，不足以单独证明报告有效，还需检查其签发、作废及成品状态。
- 草稿用 `BasedOn` 表达来源；不能仅因存在下一份草稿就让正式旧版失效。新正式修订采用 `Amended` 与 `Supersedes`。
- 同一报告的更正才进入同一版本链；不同量表、新一次评估或新一次咨询不因为日期较新就替代原报告。
- 首版正常操作形成一条单链。提交修订时检查所依据的版本仍是当前版本，避免两个窗口同时产生两个正式后继；导入发现冲突时明确提示，不按时间戳静默选胜者。
- 新版被单独作废后，旧版不自动恢复为当前有效版。
- 所有历史 PDF 保留原样，替代关系不回写旧成品。

链表无法单独表达“报告发错了，但没有新报告接替”。建议支持独立作废，直接复用现有 `EnteredInError`、`EnteredInErrorReason`/`EnteredInErrorReasonText`、`EnteredInErrorAt` 和 `EnteredInErrorBy` 表达错误签发的场景，不额外增加作废布尔字段或独立状态体系。优先通过现有报告资源的版本机制保留状态变更和既有事实，验证其前驱关系、时间及引用闭包；不覆盖已经封存的资源，也不伪造一份空白的后继 PDF。

建议普通打印仅提供当前有效正式版；被替代或单独作废的报告保留历史调阅入口，不混入普通重印。如果以后需要输出带“历史版本/已作废”标记的副本，另外生成明确标注的派生副本，原件保持不变。

仍需确认：首版是否包含独立作废、历史版本是否提供专门输出，以及正式报告是否允许单独删除。这些不影响先进行量表样张和本机渲染验证。

版本链仍须满足跨快照的契约引用闭包，必要时由交换包组织多份快照；不能为方便存储而放宽现有 `ConsultationDocument` 的单咨询约束。本机的“当前版”基于本机已知记录，不宣称是所有设备之间的全局最新版本。

### D3：报告在 Blazor 侧处理，不新增患者数据上传（已明确）

用户已明确无需围绕网络中断另行设计。报告内容准备、确认和用例编排留在 Blazor 侧及共享 Application；本机文件和打印由各宿主适配。现有账号登录与权限状态照常使用，不新增独立离线票据、离线登录或联网签发接口。

验收重点是报告路径没有新增患者数据、PDF 或指纹上传，以及未隐式触发 AI/远程重算，不要求扩展为整套离线业务系统。此项不再作为需要暂停讨论的决策点。
