# 安全基线

状态：**架构基线；具体加密配置尚未确定**

## 保护对象

EzNutrition 档案可能包含患者标识、人体测量数据、SOAP 病史、膳食记录、问卷结果、专业判断和 AI 生成内容。即使档案完全保存在本地，也应按敏感健康信息处理。

XML、XSD 和“仅本地保存”本身不提供机密性、完整性或身份认证。

## XML 导入

所有导入文件均视为不受信任输入。实现必须：

- 使用 `XmlReader` 或等价的受控流式读取方式；
- 将 `DtdProcessing` 设置为 `Prohibit`；
- 将 `XmlResolver` 设置为 `null`；
- 只加载随应用发布并经过校验的本地 XSD；
- 禁止从文档中的 URL、Schema Location 或处理指令加载网络资源；
- 对总文件大小、字符数、元素数量、属性数量、文本长度和嵌套深度设置上限；
- 在分配大型对象或构建完整 DOM 前识别格式和拒绝明显非法输入；
- 结构验证后继续执行语义验证，不把“通过 XSD”视为临床或业务正确。

具体限制值属于 V1 发布前的开放决策，必须通过边界测试和内存压力测试确定。

## 本地保存

- 默认文件名不得包含患者姓名、证件号码、SOAP 内容或诊断描述。
- Hybrid 实现应该优先使用操作系统的应用私有目录。
- 实现必须评估操作系统备份、云同步、卸载保留和共享目录行为。
- 文件写入应该使用临时文件和原子替换，防止中断破坏唯一副本。
- 覆盖前应该保留可恢复版本或提供明确的备份策略。
- 将档案导出到用户选择的位置前，UI 必须说明文件将离开应用私有空间。

## 加密与完整性

V1 是否强制加密以及采用何种密钥管理方式尚未决定。在明确方案前：

- 不得宣称明文 XML “已加密”或“安全存储”；
- 不自行设计密码学算法或字段级混淆；
- 哈希只能检测偶然损坏，不能替代带密钥的完整性保护；
- 如采用加密，应优先整包使用成熟的认证加密方案，并将密钥生命周期作为独立设计；
- 跨设备密码加密、操作系统密钥库和医院托管密钥可能需要不同的存储 Profile。

数字签名、XML 规范化和跨机构验证不属于第一条纵向链路，但档案格式不得阻止未来增加这些能力。

## 日志与错误

- 默认不记录完整 XML、SOAP、患者姓名、问卷自由文本或 AI 提示词。
- 日志应记录资源 ID、类型、Schema 版本、错误代码和必要的技术上下文。
- 解析错误消息不得回显大段患者内容。
- 为排查导入问题而导出的诊断包必须经过用户显式确认，并提供脱敏选项。

## WASM 与 Hybrid

### Blazor WebAssembly

- 上传的 XML 在内存中完成验证和解析；除非用户明确选择，否则不发送到远程后端。
- 浏览器下载后的文件不再受应用沙箱保护，UI 必须提示用户妥善保存。
- IndexedDB 实现不能假设浏览器配置、设备磁盘或操作系统备份天然安全。

### Blazor Hybrid

- 文件系统和数据库访问通过宿主服务实现，Razor UI 不直接拼接路径。
- 路径必须由应用控制并防止目录穿越。
- 移动端、Windows 和其他宿主可以采用不同的安全存储 Profile，但输出的标准 XML 语义必须一致。

## 医院实现责任

医院可以自行实现数据库和访问控制，但兼容声明至少要求：

- 不静默丢失未知资源和扩展；
- 在保存失败时保持原数据可恢复；
- 对导入 XML 使用同等或更严格的解析安全限制；
- 明确说明静态加密、备份、审计和访问控制能力；
- 通过 EzNutrition 提供的安全与兼容性测试样本。
