# V1 发布前的开放决策

状态：**需要逐项决策**

这些问题不会阻止编写架构文档，但会阻止 V1 XSD 被视为正式兼容承诺。每项决定应通过新的 ADR 或规范修改完成，而不是在实现代码中默认决定。

| 编号 | 待决事项 | 为什么重要 | 当前默认行为 | 是否阻塞首个 XSD |
|---|---|---|---|---|
| OD-001 | 核心 XML 命名空间的永久 URI | 一经发布会进入所有档案和医院实现 | 示例 URI 均视为非规范性占位 | 是 |
| OD-002 | 患者、咨询和资源 ID 的作用域及签发者 | 决定跨医院导入、去重和引用解析 | 使用 UUID 概念，不映射数据库主键 | 是 |
| OD-003 | 资源更新模型 | 影响历史审计、冲突和文件增长 | 倾向新版本资源引用 `supersedes`，不原地抹除历史 | 是 |
| OD-004 | V1 强制或可选的本地加密 Profile | 档案包含敏感健康信息 | 明文 XML 只作为交换草案，不宣称安全存储 | 否，但阻塞正式真实数据存储建议 |
| OD-005 | 参考数据集的稳定身份 | 相同输入在不同食物成分表或 DRIs 下结果不同 | 必须记录身份，具体格式待定 | 是 |
| OD-006 | AI 提示、推理内容和草稿的归档范围 | 涉及隐私、审计价值、体积和模型不确定性 | 首条纵向链路不归档 AI 数据 | 否 |
| OD-007 | 附件和二进制材料的包装方式 | 未来可能出现图片、PDF 和证书 | 不把大型二进制 Base64 塞入核心资源 | 否 |
| OD-008 | 与 FHIR 的映射边界 | 影响患者、问卷、观察和咨询模型的长期互操作性 | 借鉴 Resource/Bundle 原则，不声明 FHIR 兼容 | 否 |
| OD-009 | 未知扩展的规范化与数字签名 | 普通语义往返不等于字节级一致 | V1 首条链路只要求 XML 信息集等价 | 否 |
| OD-010 | 本地仓储的查询、事务和并发能力 | WASM 文件、SQLite 和医院 SQL 能力不同 | 公共接口先定义最低保存/读取语义 | 否 |
| OD-011 | 安全解析的具体资源上限 | 过低会拒绝合法档案，过高会产生拒绝服务风险 | 在压力测试前不写死公共数值 | 是 |
| OD-012 | 临床资料的必填与校验范围 | 过强规则会错误拒绝罕见临床情况 | Schema 只做技术完整性校验 | 是 |

## 建议的决策顺序

1. **资源身份与引用**：先解决 OD-002、OD-003。
2. **命名空间与版本标识**：解决 OD-001。
3. **首条链路的数据来源**：解决 OD-005、OD-012。
4. **安全输入边界**：通过样本和压力测试解决 OD-011。
5. **生成 V1 草案 XSD 与类型**。
6. **完成 XML 往返、迁移和未知扩展测试**。
7. **在真实档案落盘前决定 OD-004**。

## 首轮需要产品所有者确认的取舍

### 资源是不可变版本，还是可原地修改？

建议采用“资源版本不可变、修正产生新版本”的语义。这样更适合随访和历史复核，但会增加存储量与 UI 版本管理成本。

### 患者 ID 是否允许跨机构稳定？

建议区分：

- 档案内部稳定的资源 ID；
- 医院或组织签发的业务标识；
- 可选、敏感的现实身份标识。

三者不应共用一个字段，也不应默认把身份证号或医院数据库主键作为 XML 资源 ID。

### 是否在 V1 中保存 AI 数据？

建议第一条纵向链路暂不包含 AI 提示、推理过程和输出。待核心咨询档案稳定后，再单独决定哪些内容具有临床归档价值、哪些内容只应作为临时辅助信息。

### 是否立即采用完整 FHIR？

建议暂不采用完整 FHIR，但在患者、咨询、问卷和观察类资源设计前进行一次映射评估，避免无意制造无法转换的结构。
