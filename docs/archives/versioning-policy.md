# 版本与兼容策略

状态：**规范草案；V1 尚未发布**

## 目标

版本机制必须让新程序可靠读取正式发布过的旧档案，同时避免旧程序在无法理解未来数据时静默损坏档案。

## 相互独立的版本轴

档案至少记录以下版本，它们不得混用：

| 版本 | 用途 | 是否决定 XML 兼容性 |
|---|---|---|
| Bundle 格式版本 | 容器结构、Entry 与引用规则 | 是 |
| 资源 Schema 版本 | 某一资源的字段与语义 | 是 |
| 应用版本 | 记录由哪个 EzNutrition 版本写出 | 否，仅供诊断 |
| 计算引擎版本 | 说明历史结果由哪套算法产生 | 否，但影响结果解释 |
| 参考数据版本 | 食物成分、DRIs、问卷定义等来源 | 否，但影响结果复核 |

Bundle 中的资源可以具有不同 Schema 版本。读取器必须逐个识别和迁移资源，不能假设整个 Bundle 内的资源均由同一应用版本产生。

## 版本规则

### 主要版本

以下变化必须发布新的主要版本和新的 XML 命名空间：

- 删除已发布字段；
- 将可选字段改为必填；
- 改变字段含义、单位或编码；
- 改变资源标识或引用语义；
- 将原有合法文档变为非法；
- 改变未知数据的保留规则。

主要版本之间使用显式迁移器，不允许用当前 DTO 猜测旧格式。

### 次要版本

同一主要版本内只允许向后兼容的增量变化，例如：

- 增加可选元素或属性；
- 增加不改变既有值含义的枚举值；
- 放宽非安全性限制；
- 增加可忽略且可保留的扩展信息。

次要版本变化仍必须添加兼容性样本，并验证旧数据不会被重新解释。

### 应用版本

应用版本只说明写出者，不得用它决定 XML 的解析器。相同应用版本可能读写多种历史资源版本，多个应用版本也可能写出相同 Schema 版本。

## 读取流程

读取器必须按以下顺序处理输入：

```text
读取最小根信息
→ 识别 Bundle 或独立资源及其主要版本
→ 选择仓库内置的可信 XSD
→ 结构验证
→ 反序列化为对应版本 DTO
→ 执行 Vn → Vn+1 的逐级迁移
→ 业务语义验证
→ 映射为当前类型化资源
→ 返回警告、未解析引用和不支持数据清单
```

任何步骤失败都必须返回明确错误；不得降级为“尽量读取”并静默填充默认值。

## 写入规则

- 默认只写出当前正式 Schema 版本。
- 如需导出旧格式，必须有显式、经过测试的降级转换；默认不提供。
- 保存前必须完成结构与语义验证。
- 对未知扩展或未知资源无法无损保存时，必须拒绝覆盖原档案。
- 写入失败必须保持原档案可恢复，具体原子写入要求由存储实现承担。

## 兼容性承诺

### 新程序读取旧档案

每个发布版本必须保留对所有正式历史样本的读取测试。旧版本读取器和 Schema 可以保留，也可以通过逐级迁移器替代，但最终结果必须可验证且不得丢失已知数据。

### 旧程序读取未来档案

不作普遍承诺。旧程序遇到未来主要版本时必须明确拒绝。遇到同一主要版本的未来次要版本时，只有在能够保留全部未知数据且未出现未知必需功能时，才可以只读或往返保存。

### 历史结果与重新核算

- 历史结果快照是档案事实，不因当前算法更新而改变。
- 重新核算必须生成新的结果资源，并记录其来源与版本。
- UI 必须明确区分“历史结果”和“按当前版本重新核算结果”。
- 不得在打开旧档案时自动重写或升级原文件；升级写回应由用户或应用工作流显式触发。

## 正式发布一个 Schema 版本所需材料

一个版本只有同时具备以下内容才能视为正式发布：

- 不再修改的 XSD；
- 资源字段及语义说明；
- 至少一个最小合法样本和一个完整样本；
- 非法输入样本；
- 前一版本迁移测试（如适用）；
- 未知扩展保留测试；
- 安全解析测试；
- 发布说明和兼容性声明。

在这些材料齐备前，任何示例命名空间、字段或类名都属于草案。
