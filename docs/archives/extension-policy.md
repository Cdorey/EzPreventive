# 扩展与未知数据策略

状态：**规范草案；V1 尚未发布**

## 目标

医院和后续模块可以添加本地数据，但不能改变 EzNutrition 核心字段的语义，也不能让不理解扩展的程序在保存时丢失原始数据。

## 扩展边界

- 核心资源使用 EzNutrition 拥有的 XML 命名空间。
- 第三方扩展必须使用其自身控制的非核心命名空间。
- 扩展只能增加信息，不得重新定义核心元素、单位、标识或引用含义。
- 扩展不得使用与核心命名空间相似但未经发布的命名空间冒充核心字段。
- 核心 Schema 对核心元素严格验证；扩展点可以采用受控的宽松验证。

具体是使用统一 `<Extensions>` 容器，还是在少量位置开放命名空间扩展点，将在 V1 XSD 设计时确定。

## 未知扩展的处理

读取器遇到未知扩展时必须：

1. 将已知核心数据正常解析；
2. 将未知扩展作为不透明 XML 子树保留；
3. 向应用层报告存在未知扩展及其命名空间；
4. 在重新保存时保留扩展的 XML 信息集；
5. 无法保留时拒绝覆盖源档案。

“保留 XML 信息集”表示元素、属性、命名空间、文本和顺序具有等价语义；普通往返不承诺前缀、空白和属性排列与原始字节完全一致。需要字节级签名时必须使用另行定义的规范化和签名方案。

## 未知资源的处理

Bundle 可以包含当前程序不认识的完整资源。实现必须选择以下行为之一：

- 作为不透明资源保留并允许只读查看其元数据；
- 在确认可无损往返时保留并保存；
- 明确拒绝编辑或导出该 Bundle。

不得丢弃未知资源后继续保存一个看似成功但内容不完整的 Bundle。

## 数据库存储实现

将资源转换为 SQL 表的实现仍必须保留未知数据。可以采用：

- 资源原始 XML 列；
- 独立扩展表；
- 文档列；
- 已知字段关系化、未知部分保留 XML 的混合方式。

如果数据库结构无法保存未知资源或扩展，仓储实现必须返回能力错误，而不是忽略数据。

## 扩展安全

- 扩展和未知资源同样受文件大小、元素数量、嵌套深度和文本长度限制。
- 不解析扩展中的 DTD、外部实体、脚本、远程 Schema 或 XSLT。
- UI 不直接渲染扩展提供的 HTML、Markdown 或可执行内容。
- 扩展不得降低核心资源的访问控制、隐私标记或完整性要求。

## 符合性要求

未来的兼容性测试至少应包含：

- 一个具有医院命名空间扩展的已知资源；
- 一个未知完整资源；
- 相同主要版本中的未知可选核心字段；
- 读取、保存、再次读取后的语义等价检查；
- 无法保留未知数据时的拒绝保存检查。
